# Architecture and safety boundaries

1. The GUI process never enumerates handles directly. A separate invocation of the same EXE with `--scan-worker` reports a fixed-size, versioned binary record over a one-way inherited anonymous pipe. The parent only inherits the worker's file-identity/PID/match records after the child has exited. LPK6 additionally carries up to 256 unique inaccessible PIDs, the immediate Win32 error from `PROCESS_DUP_HANDLE` and the process creation timestamp where obtainable. The fixed 6,248-byte record fits the 8 KiB pipe buffer, avoiding a write-before-read deadlock. A handle inheritance allowlist restricts what is passed to the child. No user data is written to persistent logs or temp files.
2. The worker uses only query/duplicate operations. It opens a known ordinary file in its own process to learn the **boot-specific** File ObjectTypeIndex from the current system handle snapshot. It filters candidates by that index before calling `DuplicateHandle`, then excludes non-disk handles (pipes/devices) using `GetFileType` before file-identity/path queries. Within one snapshot, definite pipe/character types and confirmed different File IDs are cached by the non-null kernel FILE_OBJECT pointer; failures and unknown types are never cached. It does not use `DUPLICATE_CLOSE_SOURCE` or write to any selected file.
3. `NtQuerySystemInformation(64)` is an undocumented/unstable API. It is dynamically resolved from Windows `ntdll.dll`; its structures are kept in one component, architecture assumptions are asserted, lengths are validated before dereferencing, memory capped at 128 MiB, and retries bounded. Unexpected statuses are returned to the user rather than triggering a silent Restart Manager fallback.
4. A target is opened read-attributes only, with read/write/delete sharing when allowed. Matched volume + FILE_ID_INFO is stronger evidence than an apparent pathname match. If target identity cannot be obtained (exclusive sharing, unsupported volume), final paths are compared cautiously, and each such hit is labelled `Path (heuristic)`. **If target File ID is known but a foreign candidate File ID query fails, no final-path query is attempted on that foreign handle:** a device/AV minifilter can block such a call for many seconds. That candidate is counted as unknown/uninspectable, forces partial scan semantics, and is never treated as confirmed absent or a negative cache hit. LPK6 adds a bounded skipped-path counter without increasing the fixed IPC record size.
5. Process handles are opened with only `PROCESS_DUP_HANDLE` and, separately, `PROCESS_QUERY_LIMITED_INFORMATION`. Keeping handles open reduces PID-reuse risk. A second snapshot checks `(PID, handle value, kernel object pointer, type index)` evidence, but races are still possible. Creation times are retained where available; unexpected PID reuse is explicitly marked as an uncertain result.
6. The worker has an internal 22-second scanning budget checked between potentially blocking API calls. The parent uses a 26-second watchdog and can terminate **only the child worker it created**. Even kernel-mode hangs may delay worker termination; the GUI does not wait indefinitely for its process. Job object `KILL_ON_JOB_CLOSE` is applied when supported.
7. The UI owns the selection, scan generation, one active worker thread and optional 2-second wait timer. Selecting a new file cancels or supersedes older work. Waiting pins the selected file's volume + file ID and stops without claiming release if the path is replaced. Incomplete/error/zero-result states never imply deletion is safe.

## Security notes

- UI defaults to `asInvoker`; elevation is explicit `ShellExecuteExW` with `runas` and Windows-correct argument quoting.
- No TCP/HTTP, shell extension, driver, service, installation, registry persistence or external runtime.
- The copy-to-clipboard report groups Windows access error codes and lists each captured inaccessible PID. The parent resolves a process **basename only** when `PROCESS_QUERY_LIMITED_INFORMATION` succeeds and the PID creation time still matches the worker's record. Missing creation times and recycled PIDs are not attributed. A 256-record limit and omitted count are explicit; an access-denied error does not, by itself, establish PPL protection. No persistent diagnostics or new background tasks.
- In elevated mode the isolated worker checks its own token, attempts to enable the **existing** `SeDebugPrivilege`, validates success using token privileges, and restores its previous state on exit. Missing privileges or token errors are reported, never silently treated as enabled. This is authorized by the user's explicit admin-scan request; it is not enabled in the main GUI or non-elevated scans. Protected processes may still disallow `PROCESS_DUP_HANDLE`.
- Elevated scans use at most four native threads inside the same bounded worker process, partitioning entries by the kernel FILE_OBJECT pointer (or fair order for hidden pointers). Each native object is inspected by one thread, preserving confirmed positive/negative per-snapshot caches; a second snapshot still validates matching evidence and the parent still terminates only its own worker on a deadline. The regular scan stays single-threaded. The copied report contains privilege status, thread count and the slowest observed API stage/PID, not file names or other processes' contents.
- All scan activity stops when the application closes. The worker subprocess is not an independent daemon.
- `TerminateProcess` is limited to a worker process created by LockPeek. It is **never** invoked on a PID discovered by scanning.

## Limitations of confidence

Finding a FILE_ID_INFO match means the process had an open handle to the same file identity at inspection time; it says nothing about that handle's `FILE_SHARE_DELETE` or whether an operation will succeed. A stale or unavailable handle, symlink, reparse point, case-sensitive directory, filesystem filter or remote access may lead to false negatives or heuristic false positives. Treat output as diagnostic evidence, not a security/locking oracle.
